# Работа по проекта

## Организация

Промените по сайта и общия API са в `software/`. Firmware, хардуерни клиенти и симулационни спецификации са в `hardware/`. Преди промяна на API провери и двете части и актуализирай договора в `software/docs/devices.md`.

## Локална проверка

От `software/` изпълни `npm ci`, `npm run build`, `python -m pip install -r backend/requirements.txt` и `python -m pytest backend/tests -q`. При промяна на потребителски поток изпълни `npm run test:e2e` след инсталиране на Chromium с Playwright. Тестовете използват отделни бази и временни ключове.

TypeScript, CSS и Markdown се форматират с Prettier. Python следва Black формат. Не включвай `node_modules`, build output, локални бази, пароли, device ключове или лични данни. Нови промени в схемата изискват нов Alembic revision; не редактирай замразена миграция.

## Комити и преглед

Използвай кратко съобщение за конкретна промяна, например `feat(validator): reject tickets for another screening`. Описвай поведението, проверката и известните ограничения. При хардуерна работа добавяй схема, версии на зависимостите, инструкции за повторение и действителен резултат от симулацията. Разграничавай планиран сценарий от изпълнен експеримент.

## Сигурност и граници

Използвай само измислени картови данни. Учебният флаг за успешна транзакция не е банково потвърждение. Отзовавай компрометирани device ключове; не ги поставяй в публични Wokwi проекти. При промяна на заключването или наличностите изпълни конкурентните тестове. За различен PostgreSQL deployment резултатите трябва да се проверят отделно.
